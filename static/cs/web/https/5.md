### 原理
#### 1. http为什么不安全
* 窃听风险
* 篡改风险
* 冒充风险
#### 2. 安全通信的4大原则
* 机密性
* 完整性
* 身份认证
* 不可否认

#### 3. server 怎么把公钥安全地传输给 client ？
* server 也可以向 CA 申请证书，在证书中附上公钥，然后将证书传给 client，证书由站点管理者向 CA 申请，申请的时候会提交 DNS 主机名等信息，CA 会根据这些信息生成证书

* 这样当 client 拿到证书后，就可以获得证书上的公钥，再用此公钥加密对称加密密钥传给 server 即可

#### 4. 证书内容
* 证书序列号

* 证书过期时间
* 站点的DNS主机名（域名）
* 站点的公开密钥
* 证书颁发者的名称
* 证书颁发者的签名

#### 5. 证书的数字签名如何产生
* 1、首先使用一些摘要算法（如 MD5）将证书明文（如证书序列号，DNS主机名等）生成摘要
* 2、然后再用第三方权威机构的私钥对生成的摘要进行加密（签名）

* 3、客户端拿到证书后也用同样的摘要算法对证书明文计算摘要
* 4、client 用 CA 的公钥来给签名解密，拿到的才是未经篡改合法的摘要；
* 5、两者一笔对就可以发现报文是否被篡改了
* 备注：由于只有 CA 的公钥才能解密签名，如果客户端收到一个假的证书，使用 CA 的公钥是无法解密的，如果客户端收到了真的证书，但证书上的内容被篡改了，摘要比对不成功的话，客户端也会认定此证书非法。

#### 6. 中间人是否可以在传输过程中将正常站点发给 client 的证书替换成自己的证书呢 ？
* 答案是不行，因为客户端除了通过验签的方式验证证书是否合法之外，还需要验证证书上的域名与自己的请求域名是否一致，中间人中途虽然可以替换自己向 CA 申请的合法证书，但此证书中的域名与 client 请求的域名不一致，client 会认定为不通过！
